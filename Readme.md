# Target Generator

A small Java/Maven command-line tool that refreshes Eclipse `.target` files with new artifact versions taken from a **delivery report**. It is purpose-built for a two-party "core + customers" release workflow and is not a general-purpose target generator — but it is small enough to fork.

## The workflow this tool supports

The project sits inside a release process with two parties:

- **Core (master)** owns the package. Whenever core publishes a new version, it produces a **delivery report** listing the artifacts and their versions in that release.
- **Customers** consume the delivery report and run TargetGen to refresh their `.target` files so they pick up the new versions.

Major and minor versions are handled differently on purpose:

- **Major versions** (e.g. 1, 2, 3, … 27, 28) — the initial `.target` file is **hand-crafted in Eclipse PDE**. Eclipse walks the dependency graph and computes the exact set of required installable units, so the major-version baseline is correct by construction. This avoids the dependency-resolution headache that would otherwise have to live in this tool.
- **Minor versions** (e.g. 28.1, 28.2, …) — generated by **TargetGen** by overlaying the delivery report on top of the existing component definition. The customer is essentially bumping versions on an already-resolved set of units, not recomputing a closure.

That split is why TargetGen does not need to do PDE-style dependency analysis: by the time the tool runs, the unit set has already been chosen at the major-version baseline. TargetGen's job is to take that baseline forward through minor versions.

## Inputs

1. **`input/input.xml`** — the component definition. Lists the components, their p2 repositories, the URL pattern for each, and global options like target name format, JRE path, environment, and group filters. Customers maintain this file alongside their `.target` files; it carries the structural shape of the targets between minor versions.
2. **Delivery report** — produced by core for each release. A delimited text file (file path or URL, configured via `reportLocation` in `input.xml`) listing artifacts and their published versions. The customer flow reads this and overlays the new versions on top of the input definition.
3. **`schema/input.xsd`** — XSD used to validate `input.xml` at startup.

The tool produces one `.target` file per `<component>` in the input, written to the output directory.

## Requirements

- JDK 17 or 21 (Lombok 1.18.38 also supports newer JDKs).
- Maven 3.8+.

## Build

```
mvn clean package
```

The build runs `jaxb-maven-plugin` during `generate-sources` (one execution per XSD), then compiles, runs the JUnit 5 tests, and produces a runnable fat jar via `maven-assembly-plugin`:

```
target/targetgen-jar-with-dependencies.jar
```

## Run

The tool is a command-line application. All flags have defaults that match the project layout, so running with no arguments works as long as the working directory is the project root.

```
java -jar target/targetgen-jar-with-dependencies.jar \
    --input  input/input.xml \
    --schema schema/input.xsd \
    --output output
```

| Flag | Long form   | Default            | Description                                                                                           |
|------|-------------|--------------------|-------------------------------------------------------------------------------------------------------|
| `-i` | `--input`   | `input/input.xml`  | Path to the input XML                                                                                 |
| `-s` | `--schema`  | `schema/input.xsd` | Path to the input XSD used for validation                                                             |
| `-o` | `--output`  | `output`           | Directory the generated `.target` files are written to                                                |
| `-c` | `--compare` |                    | Diff newly generated targets against previous `.target` files in this directory or single file       |
| `-h` | `--help`    |                    | Print usage and exit                                                                                  |

### Comparing minor-version updates

Customers refreshing a target file for a new minor version typically want to see exactly what changed: which units got version-bumped, which were added or removed, and whether any repository URLs moved. Pass `--compare` pointing at the previous version's `.target` files (a directory or a single file) and the tool prints a per-component diff to stdout in addition to writing the new files.

```
java -jar target/targetgen-jar-with-dependencies.jar --compare ../previous-release/output
```

Match strategy: previous files are matched to current components by parsing the component name out of the new file's name via `targetSaveFormat`. So a current run that produces `BAG_ABC_28.1.target` will look for any `BAG_ABC_*.target` in the `--compare` directory. If multiple match, the lexicographically latest wins (so `28.0` beats `27.5`). Files in the `--compare` directory that don't match any current component are reported under "Removed components."

Within a matched pair, locations are matched first by exact URL, then by URL where exactly one path segment differs (treated as a version bump). Units inside matching locations are diffed by `id`: same id with different version → bumped (`~`), id only on one side → added (`+`) or removed (`-`).

The current report format is plain stdout text. The exit code is always 0; there is no "fail on diff" mode yet — let us know if your CI needs one.

## How a run works

1. **Validate input.** Parses and XSD-validates `input.xml` into a `ComponentInfo` model.
2. **Pick a resolver.** If `createBasedOnReport` is `true`, loads the delivery report (file or URL) and uses `ReportComponentResolver` to overlay it on the input definition. Otherwise `InputComponentResolver` resolves URLs from the input alone. Both paths share a single `RepoUrlResolver` that handles `$GROUP$` / `$ARTIFACT$` / `$VERSION$` substitution.
3. **Download.** Each distinct p2 `content.jar` is downloaded in parallel and the embedded `content.xml` extracted.
4. **Parse units.** Each `content.xml` is parsed into installable units (XXE-safe parser config).
5. **Build targets.** `TargetBuilder` is a pure function over the assembled `PipelineContext`; it produces one `Target` per component, applying the `includeGroups` / `excludeGroups` filters from the input.
6. **Write.** `TargetWriter` writes each `.target` file to the output directory.

## Input XML — key fields

See `input/input.xml` for a worked example.

- `version` — the version interpolated into `$VERSION$` placeholders. For a customer minor-version run, this is the minor version being generated (e.g. `28.1`).
- `createBasedOnReport` — `true` for the customer / minor-version flow (overlay the delivery report). `false` if the input XML is already authoritative.
- `reportLocation` — file path or URL of the delivery report. Supports `$VERSION$` substitution so a single template can point at any release.
- `reportExtensionToUse` — only delivery-report rows with this artifact extension are kept.
- `targetNameFormat` / `targetSaveFormat` — patterns for the generated target's `name` attribute and output filename. Both accept `$COMPONENT$` and `$VERSION$`.
- `groupUrlPattern` / `artifactUrlPattern` — when set to a value containing `/`, the corresponding placeholder substitutes dots with slashes (e.g. `com.example` → `com/example`). Useful for Maven-style repo paths.
- `includeGroups` / `excludeGroups` — filter installable units by id substring. `includeGroups` takes precedence; if neither is set, all units are kept.
- `components` — one `<component>` per target file; each component lists its `repository.repos.repo` entries and an optional `environment` block.

## Scope and known gaps

- **Major-version baselines are out of scope by design.** Use Eclipse PDE for those. TargetGen is the minor-version updater.
- **Unit-set deduplication across components is not implemented.** The `removeDuplicates` flag in `input.xml` is currently inert; if two components include overlapping repositories, the same units may appear in both `.target` files.
- The tool has been used primarily on Windows. The Linux/Mac path should work but is less exercised.
